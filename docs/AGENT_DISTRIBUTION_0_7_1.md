# Standalone Agent 0.7.1 for new installations

New Agent installations generated by **Sources → Add Remote Machine** could only pin a
standalone Agent labelled 0.7.0. The reviewed standalone `main` has carried 0.7.1 since
the source diagnostics release, and its current head
`31751e1e96de819c8aa899e1b53d3fc7ea3f8b08` also contains the post-dump reliability port.
The server and the browser now accept exactly `0.7.0` or `0.7.1` for
`AGENT_INSTALL_VERSION`. Nothing changes for Agents that are already enrolled.

## Root cause (proven from code)

- `backend/src/utils/agentDistribution.ts` returned 503 unless
  `AGENT_INSTALL_VERSION === '0.7.0'`, before a token was created.
- `frontend/src/utils/agentEnrollment.ts` refused to render a command for any other
  version, and the generated command checks on the host, before sudo, that
  `agent/package.json` `version` and the runtime `AGENT_VERSION` at the pinned commit
  both equal that value.
- Standalone commits `61c17d2` and later declare 0.7.1 in both places.

So a server pinned to a 0.7.1 commit with `AGENT_INSTALL_VERSION=0.7.0` creates a token,
but the copied command stops with `Reviewed Agent version does not match the
distribution.` Setting `0.7.1` instead made token creation fail with 503. The only
working option was pinning an older 0.7.0 commit, which lacks the 0.7.1 source
diagnostics and the post-dump status-check fix.

Not proven: that an operator actually ran a failing install. The finding comes from an
operator-provided configuration (0.7.1 commit, version 0.7.0) and the code above. The
disposable Ubuntu harness below reproduces both the refusal path and the fixed path.

## Change

| Area | Change |
| --- | --- |
| Server validation | `SUPPORTED_AGENT_INSTALL_VERSIONS = ['0.7.0', '0.7.1']`; any other value, including whitespace or suffixes, still returns the sanitized 503 before a token exists. The message names both versions. |
| Browser validation | The same allowlist at the rendering boundary. The generated command is unchanged apart from the version argument, so the host still verifies the pin, clean tree, package and runtime version before sudo. |
| Enrollment dialog | The post-install hint shows the configured version instead of a hardcoded 0.7.0. |
| Ubuntu enrollment harness | `scripts/validate-agent-enrollment.ps1` takes a mandatory `-AgentVersion`, and the synthetic control plane and checks use it. Node is checked against the pin in the checked-out installer. The version-mismatch fixture now uses a version that is never valid. The container `systemctl` adapter answers `show` the same way as the Agent repository's own fixture, because standalone installers since `5d5869a` check that no service is present before activation. |
| Documentation | `.env.template`, `deploy/.env.example`, the distribution contract, and in-app configuration and enrollment articles describe the two accepted versions. |

Unchanged: enrollment tokens, HMAC and nonces, command leases, Source Access, the
standalone and monorepo upgraders, existing identities, Compose forwarding, and
`ALLOW_INSECURE_AGENT_HTTP` handling. There is no migration and no new setting. Adding a
future version still needs a reviewed code change on purpose.

## Deployment and operator UAT

No database migration. No Agent update, re-enrollment or new token for existing Agents.

1. Deploy the reviewed image by digest using the normal procedure. Server first; Agents
   are not involved.
2. After the new image is healthy, set `AGENT_INSTALL_VERSION=0.7.1` in the VM `.env`.
   Keep `AGENT_INSTALL_COMMIT=31751e1e96de819c8aa899e1b53d3fc7ea3f8b08`. Apply it through
   the normal deploy or restart procedure. The order matters: an older image with `0.7.1`
   refuses to create enrollment tokens (existing Agents keep working).
3. UAT without installing anything: open **Sources → Add Remote Machine**, enter a
   synthetic machine name and a planned root, and create a token. Check that the command
   contains `git checkout --detach '31751e1e96de819c8aa899e1b53d3fc7ea3f8b08'` and
   `python3 - '0.7.1'`. Do not run it. Close the dialog and revoke the token.
4. The first real install is done on a new host when one is ready. The block must reach
   the hidden `Enrollment token:` prompt; if it prints `Reviewed Agent version does not
   match the distribution.`, record only that line and the two `.env` values.

## Rollback

- Set `AGENT_INSTALL_VERSION=0.7.0` first, then roll back the image. Old images only
  accept 0.7.0.
- With an old image, `0.7.0` plus the 0.7.1 commit brings back the original mismatch. For
  working 0.7.0 installs, also pin `AGENT_INSTALL_COMMIT` to a reviewed 0.7.0 commit such
  as `eed957edf65bdd03fb4d7b762d68ce79f869f6dc` (last 0.7.0 on standalone `main`, includes
  the ACK compatibility fix).
- Enrolled Agents are unaffected by either direction.

## Limits

- The harness uses a container `systemctl` adapter. Booted systemd, cgroup enforcement and
  pairing with the production server were not tested.
- The server does not fetch the repository. A wrong commit/version pair is still only
  caught on the host, before sudo, by design.
- Ubuntu 24.04 native acceptance for the Agent remains pending in the Agent repository.
