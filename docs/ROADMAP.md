# Fork roadmap

This public Apache-2.0 fork plans independently developed backup-management
capabilities for existing Restic environments. Use only the open-source Pluton
codebase, public Restic/Rclone interfaces, and independently written code. Preserve
upstream attribution and the Pluton name; proprietary PRO/Business implementations
and binaries are outside the development inputs.

Phase 0 delivers preparation and design documents only. Phases 1-7 are planned,
not implemented by this change. The [architecture baseline](ARCHITECTURE.md)
distinguishes current community functionality from the proposed extensions.

| Phase                                                     | Planned scope                                                                                                                                                                                                                                                          | Completion evidence                                                                                                                                                                                                   |
| --------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 0 — Repository preparation                                | Agent instructions, public-repository hygiene, architecture documentation, and existing Restic repository compatibility analysis. Analysis covers current assumptions and design questions; no production access or live compatibility certification.                  | Reviewed guardrails/design, preserved licenses and environment template, ignore-rule checks, and recorded results of existing validation commands.                                                                    |
| 1 — Legacy Restic Repository Adapter                      | Register an existing repository separately from managed plans, configure an independent password, enforce read-only access, list snapshots, inspect metadata, and filter by path/tag/host.                                                                             | Tests prove registration and inspection cannot initialize, back up, retain, prune, unlock, migrate, or otherwise write to the repository, including lock files. Compatibility is tested on disposable fixtures.       |
| 2 — Snapshot Browser and granular restore                 | Browse imported snapshot contents and restore selected files/directories into an explicitly selected staging directory. Evaluate reusable public UI components.                                                                                                        | Tests cover path containment, symlinks, platform differences, snapshot identity, cancellation, and refusal to overwrite/delete live data. Repository access stays read-only.                                          |
| 3 — Pilot migration of one backup workload                | Separately authorize and document a controlled pilot for one synthetic/example workload, such as `app-01` and `/srv/example-app`, before applying the procedure privately to a real workload. Define validation, rollback, scheduling ownership, and cutover criteria. | Recovery from a staged restore is verified; the existing legacy repository remains read-only. Any new managed writes use a separately approved destination. No automatic repository conversion or retention takeover. |
| 4 — Remote Machine / independently developed Agent        | Design and implement remote execution, authentication, capability boundaries, and lifecycle using independently written code and public interfaces.                                                                                                                    | Protocol/security review and tests for identity, authorization, disconnection, upgrades, cancellation, and scoped filesystem access. Existing public strategy hooks are not a completed agent.                        |
| 5 — Pre/Post Backup Scripts and database backup lifecycle | Assess existing community script hooks, then define the additional database dump/consistency, timeout, failure, artifact handling, and cleanup lifecycle.                                                                                                              | Tests establish execution order, failed-dump behavior, credential redaction, and safe cleanup of generic database fixtures. No production credentials in examples.                                                    |
| 6 — Automated Recovery Testing                            | Restore into isolated disposable staging environments, validate recovery results, and report failures with bounded resource use and safe cleanup.                                                                                                                      | Repeatable recovery checks cannot overwrite live data or mutate imported repositories. Tests cover partial restores and failed cleanup.                                                                               |
| 7 — Webhook and email notifications                       | Assess existing community notification code, then add the missing events/integrations for the new workflows.                                                                                                                                                           | Tested delivery/retry behavior and redacted payloads with generic destinations; existing notifications are not presented as newly implemented.                                                                        |

Each phase needs a scoped implementation task and backend tests for new behavior.
Do not enable later phases as part of preparation. Registration never implies
permission to assume ownership of an existing repository's retention or maintenance.

The next task should implement only the Phase 1 registration and inspection boundary
from [LEGACY_REPOSITORY_DESIGN.md](LEGACY_REPOSITORY_DESIGN.md), starting with local
filesystem repositories and disposable fixtures. Snapshot browsing/restore UI,
remote agents, database lifecycle, recovery testing, and notification extensions
remain later work.
