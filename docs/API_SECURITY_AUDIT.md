# API coverage and security audit

V2 follow-up: this original audit records v1. The current [172-contract matrix](API_COVERAGE_MATRIX.md) adds separate native tokens and human-approved operational requests through existing services. See [MCP v2](MCP_V2.md) for permissions, security boundaries, client evidence, rollout and rollback. OAuth remains read-only. No arbitrary API proxy, command/path access or destructive tool is added.

Reviewed baseline: fetched `origin/main` at `5126fb7`. The [160-contract matrix](API_COVERAGE_MATRIX.md) and [JSON inventory](api-inventory.json) are generated from the actual mounted route modules, controllers and explicit MCP catalog. Run `node scripts/api-inventory.mjs --check` to detect drift. All 15 existing mounted route modules are accounted for, including inline notification and persistent restore handlers. Dynamic provision/stop/resume routes are expanded.

This audit covers the public fork only. No proprietary code, production storage, infrastructure or credentials were used. The runtime delivered here is an additive read-only integration. It does not certify all existing APIs as production-ready or change managed backup/legacy repository lifecycles.

## Findings and resolution

| Finding | Evidence / consequence | Resolution in this branch |
|---|---|---|
| No multi-user RBAC or tenant ownership model | `UserController` authenticates a single configured local administrator; plan schema has no user/tenant owner. A universal API key is not delegated access. | MCP grants bind a verified IdP `sub` and `client_id` to explicit plan, Agent and storage IDs. Both token and grant scopes are required. Browser management remains local-administrator only. This does not add general application RBAC. |
| Legacy API-key allowlist uses router-relative `req.url` | `authMiddleware` lists five full `/api/...` paths, but middleware mounted inside routers observes relative paths. Its unit tests use synthetic full URLs and do not exercise that mount. `GET /api/health` is public regardless. Intended key support must not be mistaken for tested external access. | Recorded as **partially exposed**. Do not broaden this legacy path over rich DTOs merely to meet coverage. The new `/api/v1/operations` routes provide explicit scoped reads. Legacy key behavior remains a compatibility debt. |
| Existing detail methods can hydrate secrets/configuration | `StorageService.getStorage` decrypts credentials (S3 hides secret fields; other provider editor DTOs retain them); `DeviceService` spreads device records; plan/backup settings and logs contain sensitive paths/configuration. | New `OperationalReadService` uses explicit SQL/Drizzle projections. It never calls those editor serializers, exports backup contents, probes repositories, or performs storage validation. No generic internal API proxy exists. Existing administrator UI contracts are preserved. |
| No unified legacy error/response schema | Controllers use handwritten `{success,result/error}`, binary download paths and varying error handling. Some interpolate exception messages. | New external DTOs are versioned and runtime validated; fixed error codes and trace IDs; SDK validation rejections are sanitized before dispatch. Existing error contracts are inventoried, not falsely normalized. Broad legacy error hardening remains follow-up work. |
| Collections have mixed/unbounded contracts | Plans/devices/storages are not uniformly paginated; plan history and Source Access history have dedicated bounded contracts. | New read collections execute `LIMIT limit+1 OFFSET offset`, limit 1–50 and offset 0–10000. Client/activity lists use the same bounds. Existing collection APIs remain unchanged. |
| No existing OAuth authorization service | Reusing local sessions, enrollment secrets or universal API keys would confer the wrong trust. | Use an existing reviewed OAuth 2.1/PKCE IdP, resource metadata discovery and resource-bound RFC 9068 JWT verification. Pluton implements the resource server only, never fake authorization/token endpoints. No new credentials are generated or stored. |
| No safe human approval state machine for MCP writes | Existing administrator actions immediately invoke application admission/orchestration; MCP textual approval would bypass separation of duties. | All MCP writes, action requests and approval execution are **unavailable**. No `operations:request` scope or approval buttons exist. [Future approval requirements](MCP.md#write-operations-and-future-approvals) are documented. |
| Health and success states have different meanings | Primary completion, mirrors, Source Access apply, database artifacts and recovery tests are independent evidence. Detailed system health performs checks and a temporary file write. | Catalog exposes separate stored evidence, no derived universal health/success flag. Storage health is `not_measured`; no system-health tool or live snapshot traversal is claimed. Recovery returns artifact/import validation independently. |
| Agent distribution already has immutable pin safeguards | `agentDistribution` requires credential-free HTTPS repository, lowercase nonzero 40-character SHA and supported version; `AgentService.createEnrollment` validates before token generation. Frontend installer verifies checkout/version. Compose passes configuration through. | Retain `.env` authority and existing validation. No distribution database/UI or auto-update added. See [runbook](MCP.md#standalone-agent-distribution). |

## New externally reachable endpoint review

`POST /mcp` and the twelve exact `GET /api/v1/operations/...` routes accept only valid resource JWTs and the intersection of local/token scopes. Signed `sub/client_id` determine the grant; `initialize.clientInfo`, labels, request body principal fields and the caller's stated model have no authority. Resource filters execute in SQL. Nonexistent and unauthorized detail IDs both return `not_found`; failed targets are not copied into audit rows.

TLS and exact configured Host/Origin are checked before authentication; trusted-proxy interpretation is explicit. Cookies and URL-token parameters are refused. Metadata/preflight expose no operational data. IP and grant rate limits, body limits, bounded output, timeouts and static JWKS configuration reduce abuse. The configured IdP is the only outbound network dependency. No caller URL, SQL, shell command, repository operation or path is accepted. Audit writes are required before reads; a failed audit prevents dispatch.

New management routes use existing session validation **and** explicit local-administrator identity and same-origin JSON checks. OAuth/API/Agent credentials cannot manage grants. Changes to policy, grants and revocation commit atomically with audit. Revocation is idempotent; creating a duplicate subject/client pair is refused, and revoked pairs cannot be silently re-enabled. A local administrator controls all delegation; there is no claim of separate tenant administration.

Remaining risks requiring deployment review: trusted proxy/network isolation; actual IdP PKCE/resource binding and token revocation policy; provider connectivity; browser accessibility/visual validation on target devices; audit storage growth/retention; exact runtime SDK/protocol compatibility; all broader legacy API debts above. A public-facing implementation must be reviewed before enablement. No production-readiness declaration is made.
